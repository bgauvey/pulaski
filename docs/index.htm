Open-source MES · Pre-alpha

Execution for lines that never stop.

Pulaski is a manufacturing execution system for extrusion, molding, compounding and high-rate packaging lines. It takes states, counts and stops from the machines, traces lots through continuous flow, and sits beneath your ERP instead of replacing it.

What it does today

Pulaski is pre-alpha, but a lot already works end to end. Everything below is built and tested against PostgreSQL through the real handlers.

Equipment model ISA-95

Enterprise, site, area, line, unit and storage in one hierarchy, with capability flags, machine tags and shift calendars.

Orders and scheduling

Manufacturing order → work order → job → run. Planners set line and sequence; times are projected, with changeover rules, process links and batch sizes.

Processes and BOMs ISA-88

Versioned routes of operations shared across lines, single-level BOMs with approved alternates, released into fixed rows that jobs reference.

Production on the floor

Start, pause and complete runs; report good and scrap, whole batches and partial ones, capped by a believable rate. Reversals, never edits.

Machine data Sparkplug B · OPC UA · EtherNet/IP

An edge worker binds tags, buffers in SQLite through network loss and forwards. States are PackML; stops open and close on their own; alarms and process values are kept.

Downtime and OEE

Operators code stops from reason trees; supervisors split, merge and retime them. OEE by line, shift and day, with daily rollups, targets and a trend.

Inventory and lots

Lot balances by location, receipts, moves, holds, splits, merges, counts, back-dated movements and expiry. Containers, nested and mixing. GS1 labels and scanning.

Genealogy through flow

Feed points consume by time window, backflush or counter; silos and tanks are replayed FIFO or mixed, with exact, estimated or possible links in every trace.

Supply

Shortages against stock and expected deliveries, lead times, lot allocation by expiry and site preferences, hard reservation, and picking lists.

Labor

People, crews, shifts and overrides, sessions shared out to runs, breaks, approvals, qualifications, and badge-and-PIN shop-floor terminals.

Integration

A REST API, CloudEvents webhooks to the ERP with retries, and imports for materials (CSV, B2MML, OData), people (CSV, SCIM), orders and receipts.

Security and audit

Roles held per site with fine-grained permissions. Every change appends a CloudEvents record to an append-only log in the same transaction.

Built for

Mid-market process and semi-continuous plants, roughly 50 to 500 people across one to several sites, that already run an ERP.

Lines

  • Profile, pipe and sheet extrusion
  • Injection and blow molding
  • Compounding and blending
  • High-rate packaging

Deliberately not

Leaving these out keeps the core sharp and lets Pulaski fit beside what plants already own.

Non-goals for v1

  • An ERP: no accounting, purchasing, sales or MRP. The ERP stays the book of record.
  • SCADA, HMI or a historian: Pulaski reads from them and keeps only what it needs.
  • Finite-capacity scheduling: planners decide the order; Pulaski works out the times.
  • Regulated-industry features such as electronic signatures.
  • Hosted multi-tenant SaaS: self-hosted only.

Not built yet

Known gaps on the way to v1, so you don't go looking for them.

  • Quality: inspections and real-time SPC charts with rule alerts.
  • Sign-in through your identity provider (OpenID Connect). Today users have Pulaski passwords.
  • Machine counts turning into production reports; output is reported by hand.
  • A single-command demo. Today you run the API, the web app and the simulators yourself.

Architecture

Event-first: every command changes relational state and appends an event in one transaction. Only the API writes the database.

Principles

  • Standard vocabulary: ISA-95, ISA-88, PackML, B2MML, OPC UA and Sparkplug B terms, unrenamed.
  • Raw machine state is always stored; OEE categories are a per-site mapping.
  • Corrections are new events. History is never edited.

Run it locally

You need the .NET SDK (current LTS), PostgreSQL 18 and, for machine data, Docker.

  1. Get the code and load the database.

    git clone https://github.com/bgauvey/pulaski.git && cd pulaski
createdb pulaski
psql -d pulaski -v ON_ERROR_STOP=1 -f db/schema-draft.sql
psql -d pulaski -f db/app-role.sql
psql -d pulaski -f db/seed-demo.sql      # empty database only
psql -d pulaski -f db/seed-materials.sql # optional demo materials
psql -d pulaski -f db/seed-units.sql
psql -d pulaski -f db/seed-reasons.sql

  2. Start the API and the web app in two terminals.

    dotnet run --project src/Pulaski.Api   # http://localhost:5080
dotnet run --project src/Pulaski.Web   # http://localhost:5090

    Sign in as admin with the temporary password in src/Pulaski.Api/appsettings.Development.json; you'll be asked to change it.

  3. Optionally, feed it machine data from the simulated line.

    docker compose -f deploy/simulator/compose.yaml up -d
dotnet run --project src/Pulaski.Edge  # credentials from Configure → Edge nodes → Setup
