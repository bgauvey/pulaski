Open-source MES · Nearing beta

Execution for lines that never stop.

Pulaski is a manufacturing execution system for extrusion, molding, compounding and high-rate packaging lines. It takes states, counts and stops from the machines, traces lots through continuous flow, and sits beneath your ERP instead of replacing it.

What it does today

Pulaski is nearing beta, and works end to end from the machine to the ERP. Everything below is built and tested against PostgreSQL through the real handlers.

Equipment model ISA-95

Enterprise, site, area, line, unit and storage in one hierarchy, with capability flags, machine tags and shift calendars. Copy a line or a whole site to start the next one.

Orders and scheduling

Manufacturing order → work order → job → run, by hand or from the ERP. Planners set line and sequence; times are projected, with changeover rules, process links and batch sizes.

Processes and BOMs ISA-88

Versioned routes of operations shared across lines, single-level BOMs with approved alternates, and an optional approval before anything is released.

Production on the floor

Start, pause and complete runs; report good and scrap, prefilled from the machine's counts for the operator to confirm. Lots filled by reports, labels printed as they close. Corrections, never edits.

Operator stations and line boards

Operators badge in at a touch station to run jobs, report, code stops, record samples and call for help. TVs on the floor show each line's state, calls, samples and OEE, live.

Machine data Sparkplug B · OPC UA · EtherNet/IP

An edge worker binds tags, buffers in SQLite through network loss and forwards. States are PackML; stops open and close on their own; alarms and process values are kept.

Downtime and OEE

Operators code stops from reason trees; supervisors split, merge and retime them. OEE by line, shift and day, with daily rollups, targets, a trend and a stop Pareto.

Quality and SPC

Specifications with sampling plans, results by hand or from process values, control charts (X̄-R, X̄-S, I-MR, p, np, c, u) with Nelson rule alerts and capability, holds, NCRs and certificates of analysis.

Work instructions

Versioned instructions and files for an operation, material or line, shown on the job and at the station, with setup and first-article checklists and a second sign-off.

Andon, maintenance and handover

Calls for help that escalate, with response times. Maintenance requests from a stop or from preventive plans by run hours or counts. Shift handover notes and open items.

Inventory and lots

Lot balances by location, receipts, moves, holds, splits, merges, counts, back-dated movements and expiry. Containers, nested and mixing. GS1 labels, BarTender printing and scanning.

Genealogy through flow

Feed points consume by time window, backflush or counter; silos and tanks are replayed FIFO or mixed, with exact, estimated or possible links in every trace.

Supply

Shortages against stock and expected deliveries, lead times, lot allocation by expiry and site preferences, hard reservation, and picking lists.

Labor

People, crews, shifts and overrides, sessions shared out to runs, breaks, approvals, qualifications with expiry notices, and badge-and-PIN shop-floor terminals.

Integration

A REST API; CloudEvents feeds by webhook or MQTT with retries and acknowledgments; B2MML production performance. Materials, people, orders and lots from CSV, B2MML, OData, REST, SOAP, SCIM or a database, on a schedule.

Reporting

No in-app report builder: read-only report views for Power BI, Excel or a warehouse, giving the same figures as the screens.

Security and audit

Pulaski passwords or your identity provider (OpenID Connect). Roles held per site with fine-grained permissions. Every change goes into an append-only log, searchable as an audit trail.

Everyday use

Live updates, an Inbox of decisions waiting, e-mail alerts, favorites, help on every screen, translations (Spanish ships), a touch layout, a setup checklist and system health.

Built for

Mid-market process and semi-continuous plants, roughly 50 to 500 people across one to several sites, that already run an ERP.

Lines

  • Profile, pipe and sheet extrusion
  • Injection and blow molding
  • Compounding and blending
  • High-rate packaging

Deliberately not

Leaving these out keeps the core sharp and lets Pulaski fit beside what plants already own.

Non-goals for v1

  • An ERP: no accounting, purchasing, sales or MRP. The ERP stays the book of record.
  • SCADA, HMI or a historian: Pulaski reads from them and keeps only what it needs.
  • Finite-capacity scheduling: planners decide the order; Pulaski works out the times.
  • Regulated-industry features such as electronic signatures.
  • Hosted multi-tenant SaaS: self-hosted only.

Not built yet

Known gaps on the way to v1, so you don't go looking for them. The user guide keeps the full list.

  • Working offline: stations and boards say when the network is gone and keep what was typed, but don't queue it to send later.
  • Writing to machines. Pulaski reads them; machine counts become production only when an operator confirms a report.
  • Adapters for a particular ERP's or CMMS's own API, and message queues such as Kafka. Feeds are webhooks and MQTT.
  • Alerts other than e-mail.
  • Help in other languages: the guide is in English.
  • Testing with a screen reader by a person. The main flows pass automated WCAG 2.2 AA checks.

Architecture

Event-first: every command changes relational state and appends an event in one transaction. Only the API writes the database.

Principles

  • Standard vocabulary: ISA-95, ISA-88, PackML, B2MML, OPC UA and Sparkplug B terms, unrenamed.
  • Raw machine state is always stored; OEE categories are a per-site mapping.
  • Corrections are new events. History is never edited.

Try the demo

The demo needs only Docker (Docker Desktop on Windows or a Mac). Running from source needs the .NET SDK (current LTS) and PostgreSQL 18.

  1. Start the demo plant.

    git clone https://github.com/bgauvey/pulaski.git && cd pulaski
docker compose up --build

    Give it a minute, then open http://localhost:5090 and sign in as admin with the password Pulaski-demo-1; you'll choose a new one.

  2. Look around. Two extrusion lines and a packing line, with the last two shifts already recorded. Simulated PackML machines publish over Sparkplug B (Operate → Machines), a work order is running, and the extruder's melt temperature and profile width fill in live control charts. The API's e-mail lands in Mailpit at http://localhost:8025.

  3. Stop it with Ctrl+C or docker compose down; add -v to delete its data. The passwords and keys in compose.yaml are for the demo only.

Or run it from source

createdb pulaski
psql -d pulaski -v ON_ERROR_STOP=1 -f db/schema-draft.sql
psql -d pulaski -f db/app-role.sql
psql -d pulaski -f db/report-role.sql
psql -d pulaski -f db/seed-demo.sql      # empty database only
psql -d pulaski -f db/seed-materials.sql # optional demo materials
psql -d pulaski -f db/seed-units.sql
psql -d pulaski -f db/seed-reasons.sql
dotnet run --project src/Pulaski.Api     # http://localhost:5080
dotnet run --project src/Pulaski.Web     # http://localhost:5090

Sign in as admin with the temporary password in src/Pulaski.Api/appsettings.Development.json. For machine data, start the simulators with docker compose -f deploy/simulator/compose.yaml up -d and run src/Pulaski.Edge with the credentials from Configure → Edge nodes → Setup.
