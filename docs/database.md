# Pulaski — Database Reference

Oct 18, 2026 · Bill Gauvey

This is the reference for every table and column in `db/schema-draft.sql` (PostgreSQL 18). It explains what each table is for and what each column means. The SQL file stays the source of truth for exact types and constraints; when the two disagree, fix this document. Decisions referenced as D-nnn are in [domain-model-decisions.md](domain-model-decisions.md).

**Status of each table.** **In use** means the application reads or writes the table today. **Planned** means the table is designed but no feature uses it yet, so it may still change.

## Conventions

| Topic | Rule |
| --- | --- |
| Schemas | `core`: master data and current state. `ts`: time-partitioned history and rollups. `evt`: event log and outbox. `sec`: identity and access. |
| Relational or history (D-010) | If something is referenced, it is relational (`core`). If it happened, it is time-partitioned (`ts`). |
| Ids (D-006) | Every `id` is a native `uuid` holding a UUIDv7, generated by the application. The `uuidv7()` column default is only a backstop for manual scripts. Never sort ids in .NET; sort in SQL. Never read time out of an id. |
| Business keys | Codes and numbers (equipment code, order number, lot number) are separate unique columns, never primary keys. |
| Status and kind columns | `text` with a `CHECK` list, not PostgreSQL enums, so values can be added without `ALTER TYPE`. |
| Quantities | `core.qty` is a domain over `numeric(18,6)`. |
| Concurrency | No version columns. The application reads `xmin::text::bigint AS version`, locks the row `FOR UPDATE`, compares and writes. A mismatch is a 409. |
| `created_at` / `updated_at` | When the row was inserted and last changed, set by the application in the command's transaction. |
| Partitioned tables | Range-partitioned by a time column, monthly by default (`ts.create_month_partitions`). The primary key always includes that column. There is no default partition: a missing partition makes inserts fail, so the API keeps three months ahead through `ts.ensure_partitions` (D-028). |
| Migrations (D-028) | `schema-draft.sql` is the complete schema for a new database; each change also ships as a re-runnable `db/migrations/NNNN_*.sql`, applied by `db/migrate.sh` and recorded in `public.schema_migration`. |
| Foreign keys into history | None. A row pointing at a partitioned table stores the id (and its time) without an FK, so old partitions can be dropped. |
| Deletes | The application role (`pulaski_app`, `db/app-role.sql`) has `DELETE` only on `core.equipment_tag`; other master data is deactivated. Events and time-partitioned history are never deleted. |

## 1. Reference data

### core.uom — units of measure (D-026) · *In use*

The unit catalog. A unit with a factor converts to every other unit of its dimension, for every material. A packaging unit (box, bag, pallet) has none and converts only through a material's own conversion. `db/seed-units.sql` loads the standard metric and US units with their exact factors.

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `id` | uuid | no | Primary key. |
| `code` | text | no | Unique short code: `kg`, `m`, `ea`, `box`. Fixed once created. |
| `name` | text | no | Display name. The only thing besides `is_active` that can change. |
| `dimension` | text | no | `mass`, `length`, `count`, `volume`, `area`, `time`, or `other` for packaging. Fixed once created. |
| `to_base_factor` | numeric(24,12) | yes | How many of the dimension's base unit one of this is (1 lb = 0.45359237 kg). The base unit has 1. Null only for `other` (packaging). Positive. Fixed once created, since quantities are stored in the unit. |
| `is_active` | boolean | no | Inactive units are not offered for new entries; quantities already in them still convert. |
| `created_at`, `updated_at` | timestamptz | no | See conventions. |

### core.packml_state — PackML states · *Planned (seeded)*

The 18 PackML `StateCurrent` values, keyed by their standard number (D-005). Seeded by the schema script.

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `code` | smallint | no | Primary key, 0–17. 0 `Undefined` is not a PackML state; Pulaski uses it for "no signal", so lost time stays visible. |
| `name` | text | no | Unique standard name (`Execute`, `Held`, …). |
| `is_acting` | boolean | no | True for transient "-ing" states (`Starting`, `Stopping`, …). |

## 2. Equipment model (ISA-95 Part 2)

### core.equipment — every piece of the plant hierarchy · *In use*

One self-referencing table holds enterprise, sites, areas, work centers (lines), work units (machines) and modules. `level` and `equipment_role` say what each row is.

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `id` | uuid | no | Primary key. |
| `parent_id` | uuid → equipment | yes | The containing equipment. Null only for the enterprise (`equipment_root_ck`). |
| `site_id` | uuid → equipment | yes | The owning site, copied down for fast filtering. A site points to itself; only the enterprise has none. |
| `code` | text | no | Business key, unique within the site (`equipment_code_uq`). |
| `name` | text | no | Display name. |
| `description` | text | yes | Free text. |
| `level` | text | no | ISA-95 level: `enterprise`, `site`, `area`, `work_center`, `work_unit`, `equipment_module`, `control_module`. |
| `equipment_role` | text | no | What the row does at that level, e.g. `production_line`, `machine`, `feed_point`, `storage_zone`. Valid level/role pairs are listed in `equipment_level_role_ck`. |
| `tracks_state` | boolean | no | Has PackML state, downtime and OEE. |
| `is_schedulable` | boolean | no | A planning target: jobs can be planned to it, a line or a group such as a department (D-022). |
| `can_run_job` | boolean | no | Jobs actually run here (a line or cell). A schedulable row without it is a group: its jobs wait in a window until a line below it that can run jobs takes them (D-022). |
| `holds_inventory` | boolean | no | Lots can be located here (storage, feed point). |
| `single_material` | boolean | no | Takes one material at a time (D-032): another material can arrive only when the quantity of the one there is zero. Needs `holds_inventory`. |
| `commingles_lots` | boolean | no | Lots here mix and can't be told apart, like a silo or tank (D-031): every arrival joins one balance per material. Needs `holds_inventory`. |
| `flow_model` | text | no | How a balance here flows, for genealogy (D-060): `mixed` (default; a withdrawal takes a share of every arrival still there) or `fifo` (plug flow, oldest first). |
| `min_residence` | interval | yes | The least time material stays before it can leave (D-060); taken sooner, an arrival is only possible. |
| `state_derivation` | text | no | Where its state comes from (D-050): `own_tags` (default, its own state tag), `series` (the worst state of its machines), `parallel` (the best) or `constraint_machine`. Set on the Equipment screen; nothing reads it until machine data is collected. |
| `constraint_equipment_id` | uuid → equipment | yes | The constraint machine: set exactly when `state_derivation = 'constraint_machine'` (`equipment_derivation_ck`), and equipment below this one that tracks state. |
| `micro_stop_threshold` | interval | no | Stops shorter than this are micro-stops (D-050): logged, not queued for coding, not availability loss. 0 to 60 minutes (`equipment_micro_stop_ck`), default 5. |
| `machine_profile_id` | uuid → machine_profile | yes | The machine profile its state and stop codes are read with (D-050). Only equipment that tracks state takes one, of its own site. |
| `time_zone` | text | yes | IANA zone, required on sites. Shift times and reports use it. |
| `is_active` | boolean | no | False when retired. |
| `calendar_mode` | text | no | Which working time it follows for planning (D-038): `inherit` (default, its parent's; at the top with nothing set, around the clock), `schedule` (its own) or `around_the_clock`. |
| `shift_schedule_id` | uuid → shift_schedule | yes | Its own schedule; set exactly when `calendar_mode` is `schedule` (`equipment_calendar_schedule_ck`). A schedule of its own site. |
| `created_at`, `updated_at` | timestamptz | no | See conventions. |

### core.equipment_closure — ancestor/descendant pairs · *In use*

Every ancestor/descendant pair, including each row with itself at depth 0. The application maintains it on insert. It answers "everything under this area" and scoped permission checks without recursive queries.

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `ancestor_id` | uuid → equipment | no | The higher row. Part of the primary key. |
| `descendant_id` | uuid → equipment | no | The lower row (or the same row at depth 0). Part of the primary key. |
| `depth` | smallint | no | Levels between them; 0 for self. |

### core.edge_node — Pulaski Edge nodes · *In use (D-050)*

A worker on plant hardware that reads machines through its connections, buffers what it reads and forwards it. It signs in as a local user holding the Edge node role (`edge.ingest`) at the site. Maintained on Configure → Edge nodes (`equipment.manage`).

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `id` | uuid | no | Primary key; the edge's `EdgeNodeId`. |
| `site_id` | uuid → equipment | no | Its site. |
| `code` | text | no | Upper case, unique per site (`edge_node_code_uq`), fixed once created. |
| `name`, `description` | text | no / yes | Display name and notes. |
| `is_active` | boolean | no | Off: Pulaski refuses its data and the edge stops collecting. |
| `stream_id` | uuid | yes | The edge's buffer, as of its last batch. A new buffer is a new stream. |
| `last_sequence` | bigint | no | The highest sequence number of `stream_id` applied; a batch at or below it is skipped, so sending again is harmless. |
| `last_seen_at` | timestamptz | yes | When it last forwarded signals or reported what it sees. |
| `agent_version` | text | yes | The version of Pulaski Edge it runs. |
| `created_at`, `updated_at` | timestamptz | no | See conventions. |

### core.equipment_tag — machine signal bindings · *In use (D-050)*

One signal an edge reads for a piece of equipment, and what it means. One active tag per role on a piece of equipment, process values aside (`equipment_tag_role_uq`), and one per address on a connection (`equipment_tag_source_uq`). A tag may be physically deleted by equipment maintainers; any quality-characteristic source binding is cleared first. The deletion event and time-series history remain.

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `id` | uuid | no | Primary key; the edge's signals name it. |
| `equipment_id` | uuid → equipment | no | Equipment of the node's site that tracks state. |
| `tag_role` | text | no | `state`, `unit_mode`, `stop_reason`, `processed_count`, `defective_count`, `consumed_count` or `machine_speed`; `level` (a silo's or tank's, D-060) can be bound but isn't read yet; `alarm`, `warning` and `process_value` aren't recorded yet. |
| `connection_id` | uuid → edge_connection | no | Where it is read. |
| `source_address` | text | no | Sparkplug B: `group/node[/device]:metric`. |
| `uom_id` | uuid → uom | yes | Unit of the value; not used yet. |
| `scale_factor`, `scale_offset` | numeric(18,9) | no | Counts are multiplied by the factor; a speed is value × factor + offset. Defaults 1 and 0. |
| `counter_rollover` | bigint | yes | Counters only: the value the counter wraps at. Without it a counter going back is taken as reset to zero. |
| `deadband` | numeric(18,9) | yes | Process values only; not used yet. |
| `is_active` | boolean | no | Off: its signals are skipped. |
| `created_at`, `updated_at` | timestamptz | no | See conventions. |

### core.lot_allocation — stock set aside for a job (D-064) · *In use*

A quantity of one lot, in its base unit, kept for one of a job's planned components. Active rows are left out of what other jobs see as free (recommendations, shortages); consuming the lot into the job lowers its row (to `consumed` at zero). Released or used up, never deleted. Changes lock the job, then the lots in id order, then their active allocations (`FOR UPDATE`, id order), as declarations do (D-027).

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `id` | uuid | no | Primary key. |
| `site_id` | uuid → equipment | no | The job's site. |
| `job_id` | uuid → job | no | The job it is for. |
| `material_id` | uuid → material | no | The component (the lot's material). |
| `lot_id` | uuid → lot | no | The lot. One active allocation per job and lot (`lot_allocation_active_uq`); more is a top-up. |
| `quantity` | qty | no | Still set aside, in the lot's base unit; 0 once used up. |
| `allocated_qty` | qty | no | As set aside, plus any top-ups. |
| `status` | text | no | `active`, `consumed` (used up by consumption into its job) or `released`. |
| `basis` | text | no | `chosen` by a person, or `recommended` (taken from the suggestion). |
| `note` | text | yes | The suggestion's reason, or why it was released or trimmed; at most 500 characters. |
| `created_at`, `created_by` | timestamptz, text | no, yes | When and by whom. |
| `ended_at`, `ended_by` | timestamptz, text | yes | When and by whom it stopped being active; set exactly when not active (`lot_allocation_ended_ck`). |
| `updated_at` | timestamptz | no | Last change. |

### core.partial_batch — batches cut short when a line stopped (D-036) · *In use*

A partial batch is reported only as a run ends with a reason (or later, into a run that did), at most one per run (`partial_batch_run_uq`, a unique index that leaves out `reversed` rows), in a lot of its own. Under the `exact` rule it waits on hold for a decision. Reversing its report (D-063) marks it `reversed`, so the run can report another.

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `id` | uuid | no | Primary key. |
| `job_id` | uuid → job | no | The job. |
| `run_id` | uuid → job_run | no | The run it belongs to. Unique: one partial batch per run. |
| `lot_id` | uuid → lot | no | Its lot: on hold while `pending`, released when approved, written off when rejected. |
| `quantity` | qty | no | How much it held, in `uom_id`. |
| `uom_id` | uuid → uom | no | The material's base unit. |
| `batch_size`, `batch_rule` | numeric(18,6), text | no | The material's batch size and rule when it was reported. |
| `status` | text | no | `accepted` (near rule), `pending`, `approved`, `rejected` or `reversed` (its report was reversed, D-063; a rejected one can't be). |
| `occurred_at` | timestamptz | no | When it counts as made. |
| `reported_by` | text | yes | Who reported it. |
| `decided_at`, `decided_by` | timestamptz, text | yes | When and by whom it was approved or rejected: set for a decision, empty while undecided, either for a reversed one (`partial_batch_decided_ck`). |
| `decision_comment` | text | yes | Why, at most 1000 characters. |
| `scrap_reason_code_id` | uuid → reason_code | yes | For a rejection, the scrap reason. |
| `created_at`, `updated_at` | timestamptz | no | See conventions. |

### core.material_uom_conversion — a material's own conversions (D-026) · *In use*

Conversions true for one material only: 1 m of a profile weighs 1.6 kg, a box holds 500 end caps. Each works both ways and combines with the standard factors (with m to kg, feet convert to pounds). A material's conversions never give two routes between the same units, so every conversion has one answer; a pair is stored one way only.

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `material_id` | uuid → material | no | The material. Part of the primary key. |
| `from_uom_id` | uuid → uom | no | Source unit. Part of the primary key. |
| `to_uom_id` | uuid → uom | no | Target unit; never the source unit. Part of the primary key. |

### ts.lot_event — every inventory movement · *In use*

`core.lot` quantity and location are the running result of these rows. The application appends one row per movement and lot (D-027), in the base unit; it never updates or deletes them. The movement journal (D-029) reads it by site and time range, helped by a BRIN index on `occurred_at`. A back-dated movement (D-057) is recorded now and counts from `effective_at`: stock at a time is the sum of `qty_delta` of the rows that count by then, so it is the same whatever order movements were entered in. A reversal (`reversed`, D-030, D-063) is a row of its own; a reversal of a declaration or of an earlier movement counts at the original's `effective_at`, and the two are then left out together when checking a lot's history never goes below zero.

### evt.event — the append-only event log (D-004, D-007, D-008) · *In use*

### evt.delivery — one event's delivery to an adapter (D-061) · *In use*

The queue and record of what was sent where. A row is added for each matching event when it is captured (once: unique per sink and event), and changed only by the sender (attempts, outcome) and by operators (retry, skip) on **Configure → Integrations**. A `pending` row waits while an earlier `pending` or `failed` row of the same sink and subject exists (it is *held*), so the receiver sees each lot's events in order. The app role has SELECT, INSERT and UPDATE; rows aren't deleted.

| `event_type` | text | no | The event's type: `pulaski.lot.received.v1`. |
| `subject` | uuid | no | The event's subject (a lot); what later deliveries are held behind. |
| `status` | text | no | `pending` (to send, or retrying), `delivered`, `failed` (gave up: refused, or attempts ran out) or `skipped` (an operator decided it won't go). |
| `attempts` | integer | no | Attempts so far. A retry carries on counting. |
| `next_attempt_at` | timestamptz | no | When a pending row is next due; growing waits after each failure, now after a retry. |

### ts.create_month_partitions(parent, from, months) — function

Creates monthly partitions (UTC bounds) for a partitioned table, starting at the month of `from`, for `months` months. Safe to re-run. `ts.ensure_partitions` calls it for every partitioned table; the tests also call it directly for the month before.

### ts.ensure_partitions(months) — function (D-028)

Creates the current month and the next `months` − 1 for every range-partitioned table in `ts` and `evt`, by calling `ts.create_month_partitions` for each, and returns how many partitions it created (0 when all were there). `months` is 1 to 24. `SECURITY DEFINER`, with a fixed `search_path`: it runs as the schema owner, since creating a partition needs ownership of its parent. Only `pulaski_app` may execute it. The API calls it at startup and every 12 hours with 3; the seed calls it once.
